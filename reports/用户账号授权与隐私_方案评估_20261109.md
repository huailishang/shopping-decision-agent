# 用户账号授权与隐私方案评估（2026-11-09）

结论：可以研究“用户在官方页面登录、对指定任务授权、智能体读取必要数据”的方案；登录本身不授予全部数据访问权，也不替代平台对本应用和业务用途的准入。正式产品优先平台批准的接口；本机实验可考虑平台允许范围内、用户主动触发的商品页信息提取。当前不应为了选打印机就同时接管京东和支付宝账号。

本轮仅研究和记录，没有实施账号集成、接管浏览器、读取 Cookie/密钥、授权支付或修改既有业务实现。原 P0.7 误判及入口脱节问题保持待修；用户登录不能解决这些内容错误。

## 1. 千问、元宝的公开实践能证明什么

- 千问公开的[隐私政策](https://terms.alicdn.com/legal-agreement/terms/privacy_policy_full/20231011201849846/20231011201849846.html)分别列出账号绑定管理与应用授权管理；其[第三方信息共享清单](https://terms.alicdn.com/legal-agreement/terms/privacy_description_of_sharing/20240716181048950/20240716181048950.html)明确披露通过淘宝接口开展商品查询及必要信息流转。因此可借鉴的是平台合作、接口接入、分项授权和可撤销管理；不能由此推断普通开发者登录同一账号即可得到等价能力。
- 本次定位到[腾讯元宝官方隐私政策入口](https://privacy.qq.com/document/preview/eb9be56572ab4886b6ca124e72abf413)，正文依赖 JavaScript，当前研究工具未取得可读正文。未核得元宝以相同方式连接京东、支付宝买家账号的官方依据，不将该能力作为本方案已证实前提。第三方政策档案只用于发现官方链接，不作为产品实现证据。
- 以上公开材料没有披露两家的完整内部架构。本报告的连接器、字段过滤与策略校验属于我们的设计建议，不能写成它们已经采用的内部实现。

## 2. 必须分别取得或落实的权限

| 层次 | 具体内容 | 不自动包含的能力 |
| --- | --- | --- |
| 平台应用准入 | 开发者身份、应用审核、适用主体资格、接口权限、用途/展示/保存/转交限制、必要签约 | 用户愿意登录不替代平台审核 |
| 用户资源授权 | 按平台实际支持的范围授予特定应用访问权，并记录账号、目的、期限与撤回方式 | 头像/账号标识授权不含所有订单、地址、账单 |
| 本次任务操作授权 | 本次查哪些商品、哪些地区、允许读什么；读、加购、填单、提交订单、付款分别限制 | 一般购物意图不等于付款指令 |
| 数据处理边界 | 哪些字段本机处理、是否发给模型服务商、保存多久、谁可查看及删除方式 | 允许连接京东不等于允许将所有页面上传云端 |

建议先按业务需要反推权限，避免为了“接通账号”先收集所有数据。

| 目标 | 实际需要核实的能力 | 本项目近期选择 |
| --- | --- | --- |
| 建立身份关联 | 官方登录/用户标识能力及相应应用权限 | 可选；纯商品比较不必强制账号绑定 |
| 搜索商品、读取公开规格 | 获准商品查询接口与用途条件 | 优先申请；公开查询不应默认要求买家登录 |
| 核会员价、券资格、地区库存 | 平台确实开放的个性化报价能力，或获准的本机页面核验 | 单独验证字段；不能保证登录后即可完整取得 |
| 获取历史订单、收货地址 | 平台确实开放的对应用户数据接口、必要用途与授权 | 第一版不收集；不得借商家/推广结算接口冒充消费者全历史 |
| 支付宝身份信息 | 对应身份服务权限及用户授权 | 选购比较当前没有充分必要性 |
| 支付宝付款 | 对应支付产品准入、签约、交易授权与受控结果核验 | 转支付实验台另验；本仓保持逐单确认与交易关闭 |

京东登录凭证不能自动成为全站商品库、所有个人数据或任意操作的通行证；支付宝登录也不会自动开放京东账户数据或支付全部账单。两平台账号关联还会增加跨平台识别用户的风险，应只有在明确业务确实需要时再做。

## 3. 两条可以落地的接入路线

### A. 正式接口与开放授权：正式产品优先

1. 向现行开放平台核准具体应用类型、主体资格、商品池与字段权限。京东现有官方资料介绍了审核应用后的授权码流程；迁移公告区分商家开放平台与联盟等独立入口，不能直接把旧 JOS 示例视作现网接入成功。
2. 用户点击连接后，在平台官方浏览器页面或官方 App 内完成认证及授权。平台返回短时授权码，再由受信组件换取访问凭证；模型不接触密码或令牌。
3. 调用前检查平台实际授予的范围、本项目允许动作、本次任务对象和有效期。后续扩大用途或增加写操作，应重新授权。
4. 身份、商品数据和支付使用不同工具及策略；支付结果必须由可信回传/查询确认，不依赖模型口述。

安全实现参考 [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) 和 [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700)：桌面授权优先系统浏览器；回调与发起会话绑定、校验 state、短时码和安全回调；按平台能力核实并落实 PKCE。没有核实京东/支付宝某一具体产品支持 PKCE 前，不写成现成可用配置。不能给不支持保密凭证的桌面客户端硬塞共享生产 Secret。

部署要区分：

- **当前本机原型**：仓库约束仍是会话和 API key 本机保存。必要凭证交本机受控组件/系统安全存储，不进 Git、对话、日志或云模型。若官方接口只允许保密服务端换票，这就是需解决的架构前置，不能假装纯桌面已完成正式接入。
- **未来多用户服务**：如平台要求服务端签名/换票，共享应用私钥应在可信服务端密钥系统，用户令牌须隔离、加密和可撤销。这会改变当前“仅本机”的部署边界，需另行明确数据处理、准入和授权，不能静默将本机令牌搬上云，也不能把应用私钥打进分发给用户的 Java 安装包。

### B. 本机用户参与的商品页提取：条件具备时的小实验

用户自己在正常京东浏览器页面登录，程序在认证期间暂停页面采集。用户选定商品页后，点击“读取此页商品信息”，本机连接器提取白名单字段并先展示预览，再交比较引擎。若平台不允许相关自动化或无法核实适用条款，则使用用户主动提供的链接/必要字段，不绕登录或风控限制。

可参考 Chrome [activeTab 权限](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)的用户手势与临时当前标签页授权。它只是缩小浏览器访问面，并非平台数据许可，也不天然限制为只读：带脚本执行能力的扩展仍可能点击、读取额外内容。因此还需本机程序限制域名、页面类型、字段和动作，避免把通用脚本/浏览器调试入口直接交给模型。当前页访问可能在同源导航后继续，不能宣传为自动逐页重新授权。

该路径不读取或导出 Cookie、不扫描用户整个浏览器资料目录、不连接可操纵所有标签页的通用远程调试端口。优先不申请 cookies、history、所有网站等权限；需要长期授权时再按来源逐项申请。断开智能体访问后，平台浏览器是否保持登录由用户掌握；关闭连接与平台退出登录是两个操作。

此路线可以补少量用户所见价格条件，但其稳定性、完整性和平台许可弱于获准业务接口；页面所见报价必须保留选中配置、适用条件、地区和时间，不保证最终结算金额或库存锁定。

## 4. 数据如何经过模型而不泄露整个账号

建议的数据流：

```text
用户在官方页面/App完成认证
            ↓
受控连接器保管会话/授权凭证
            ↓  每次检查任务、对象、字段、动作、期限
获准API返回或用户主动选择的商品页
            ↓
本机提取、去除身份字段、用户预览
            ↓
商品ID/型号/店铺/选中配置/价格条件/地区范围/来源时间
            ↓
购物比较与解释
            ↓
用户选择；订单/支付另行交接与逐单确认
```

具体落实：

1. **凭证和模型隔离**：模型只请求“核验这三个商品”等窄工具，连接器负责鉴权。输入、工具返回、错误和审计日志均不得带令牌、密码、验证码、完整 Cookie、支付凭证。
2. **采集前先缩小范围**：不先把完整 DOM、截图、网络报文送到云端再脱敏。仅提取必要字段；手机号、详细地址、银行卡、账单和订单列表默认不进入比较链路。省市区够核价时不收门牌号。
3. **本机存储也要受控**：系统安全存储/加密、当前用户访问限制、短时缓存。`.gitignore` 只能防误提交，不能代替加密和权限控制。留本机也不等于已防住本机恶意软件或管理员权限。
4. **权限由程序执行**：工具调用逐次检查白名单；网站文字只能当外部证据，不能改变授权或触发支付。单看 HTTP 方法或模型承诺“只读”都不足以保证没有副作用。
5. **用户能理解和撤回**：显示当前连接账号的掩码、目的、字段、有效期和最近访问记录。撤回立即阻断新调用及令牌刷新，清理不再必要的缓存；平台支持时同步撤销上游授权。依法需留的最小记录另行限定用途和期限，不承诺全部瞬时删除。
6. **云端另有边界**：若调用云模型，需核对供应商角色、实际传输内容、留存/训练用途及跨境路径。去掉姓名不一定构成匿名化，SKU、历史订单等组合仍可能关联个人。“凭证未出本机”不能用于宣传全部数据未出本机。

产品中的授权描述应具体，例如：“本次核验你选定的 3 个京东商品；读取型号、店铺、配置、所见价格与优惠条件、地区库存提示；默认不读取订单历史与收货人信息。开始前预览将发送给模型的字段，可随时停止。”数量与本地任务期限属于我们的产品限制，不是声称平台支持同名细粒度 scope；本地任务结束也不会自动让平台令牌失效，应另做撤销/过期处理。

## 5. 个人信息处理要求

依据[《个人信息保护法》](https://www.samr.gov.cn/wljys/gzzd/art/2023/art_3ef1e889c1e644d4b65b5f5c7f432386.html)，需明确目的、最小范围、期限和撤回方式；金融账户属于敏感个人信息，处理应满足特定目的、充分必要性、严格措施及相应同意要求。面向他方提供、委托处理和境外提供的适用义务不同，须按模型供应商与我们的实际关系判断；相关情形应事前做个人信息保护影响评估。不能用一次账号登录同意覆盖所有后续共享、训练和支付。

这不意味着每次只看一个公开商品都需要读取个人信息或接入支付服务。近期应优先减少需要处理的个人数据，并确认平台允许的具体业务用途。

## 6. 本项目建议的最小下一步

近期目标限定为**少量京东销售项的只读、可审计核验**，支付宝暂不作为商品比较的前置。保留无需登录的使用路径，分别记录商品发现数量与有效个性化报价数量。

正式 API 路线先取得当前入口对本应用的书面/后台可核权限与字段说明；本机页面路线先核平台条款、浏览器扩展权限和本机工具边界，再安排用户主动参与的小实验。第一轮用少量明确销售项检查：SKU/型号与套餐、店铺、所见价格与资格、地区库存提示、获取时间。未取得的字段继续未知。

验收除了正常读数，还应实际检验：拒绝越界访问订单/地址；撤回即停止；切换账号不混数据；页面诱导下单无效；工具输出和日志无凭证；过期价格不得继续通过；用户能预览数据去向。之后才考虑订单草稿或支付实验台的另一次交接。
