## 2. 需要先修的问题

### R1 / P1：可见性和型号作用域不确定时仍给错误肯定

位置：`shopping_decision/official_detail_text.py:30`、`:102`；型号正则在`:10`只识别HL系列。

新增14个手选故障/阳性控制中，3个符合预期，9个错误肯定，2个明确阳性降为未知。这不是随机样本，不报告总体错误率，也不否认当前三份真实官网原文重放成功。

| 新输入类型 | 实际结果 | 应有行为 |
| --- | --- | --- |
| CSS后代`.wrap .secret`、属性选择器、纯标签`aside`、复合类`.spec.secret`共4例隐藏无线文字 | 4例`wireless=true` | 不支持这些选择器时应降级/限取明确正文，不能把隐藏文字确认为证据 |
| `DCP-B7658DW`或`MFC-L5728DW`支持无线，HL-10W仅USB，共2例 | 2例`wireless=true` | 不得把其他系列型号功能借给当前型号 |
| 其他型号章节、跨句否定更正、后一句“以上仅适用其他型号”，共3例 | 3例`wireless=true` | 保留作用域/矛盾，不能取第一个肯定就返回 |
| `opacity:0.5`的可见肯定 | `wireless`未知 | 半透明不等于隐藏；现有正则把0.5的前缀0当0 |
| “与HL-B2188DW相比，HL-10W同样支持无线” | 未知 | 明确当前主体的比较句存在有效性损失；可保守弃权但须如实记录能力限制 |
| 无线肯定但否定另一功能、继承隐藏、非完整嵌套隐藏，共3例 | 符合预期 | 保留这些阳性/负向控制 |

根因不是少几个关键词：复杂隐藏规则直接跳过而内容照读；句号/DOM作用域被压平；型号检测限HL；`supported_phrase`在发现第一个局部肯定后返回，未综合同功能后续否定。

修复方向：保留主张所在DOM区域、主体及相邻限定，处理同功能矛盾；无法判断可见性或型号归属就明确未知，必要时只使用已核的正文范围。不要再仅堆已暴露词条，也不要求实现完整浏览器/CSS引擎。继续保留三份实页阳性，防止全部丢为未知。

### R2 / P2：离线报告可通过提示字段带入嵌套推广链接、价格和伪批准

位置：`shopping_decision/discovery_pool.py:96`及相邻字段；正常CLI的`--haina-report`直接读JSON后调用此函数。

在合法合成报告内，将`brand_hint`改为包含合成推广URL、`price`、`purchase_recommendation_approved=true`的对象，候选池直接透传，实际CLI输出也出现该对象。模块虽然校验顶层状态、无ID、时间和标题，但没有重新校验提示字段的类型/长度、列表元素及派生枚举。

这是**报告读取边界的字段隔离失败**，不是已执行交易：外层购买/交易仍false，正式平台候选仍0，嵌套批准没有被执行。原始合成API响应经正常导入器处理时，伪造ID/价格/score/评论等字段仍被忽略；不能把这一点扩大为任何离线报告均安全。

修复方向：把离线报告也视为未受信任输入，逐字段检查/重建有限字符串、型号列表和状态，拒绝嵌套对象及越界字段；不要依赖外部写的`synthetic_test`标签证明真实来源或安全。保留无ID线索可见但不进平台候选池的行为。

### R3 / P2：Windows默认测试命令不能复现310/310

位置：`tests/test_haina_ingest.py:162`的子进程只指定父进程UTF-8解码，未统一子进程编码；其他离线CLI测试也有隐式本机编码。

实际在Windows Python3.12.3执行：

| 环境/命令 | 实际结果 |
| --- | --- |
| 默认`python -m unittest discover -s tests -q` | 310项，1个ERROR：海纳正常CLI输出UTF-8解码失败，继而`proc.stdout=None` |
| 只设`PYTHONIOENCODING=utf-8`再跑全量 | 海纳项恢复，但京东联盟/淘宝物料2项用GBK解码UTF-8子输出失败 |
| 同时`PYTHONUTF8=1`及`PYTHONIOENCODING=utf-8`再跑 | 310/310通过，12.269秒 |

这不否定执行者在Linux/Bash下的历史通过，但Windows主开发环境和文档默认命令存在缺口。临时环境设置用于定位原因，不算修复。应统一CLI管道输入输出和测试父子进程编码，并保留无需额外环境变量的Windows回归。
