# 动态品类选择框架：跨商品复用方向（待评估）

> 提出时间：2026-11-02；性质：**架构假设 / 供独立评估者审查**，不是已批准的设计或执行包。
> 权威流程入口仍是 `CURRENT.md`；当前 H08 B 的冻结范围与验收标准不因本备忘录自动改变。

## 1. 要解决的根本问题

打印机、空调、净水器、儿童学习机的关键选择维度明显不同。若每新增一个品类就编写新的 `if/else`、交互表单和推荐算法，系统最终会变成一批品类专用工具，而不是通用购物智能体；若所有品类都套同一组分数和统一问题，又会错过真正决定选购的专业约束。

**待评估假设：固定通用购物决策流程，让品类选择框架按需发现、校验、缓存和复用。动态产生的是可校验的数据/配置，不是在运行中生成并执行任意新程序。**

区分三件事：
- **稳定的通用程序**：需求确认、约束管理、按需检索、来源与适用性审核、路线/商品比较、证据引用、未知项呈现、版本追踪、交易授权边界。
- **动态的品类选择框架**：本品类有哪些技术路线和关键指标，什么用户答案会改变结论，需检索哪些证据、怎样比较、有何反例。这只是候选研究框架，**尚不是已证实的购买规则**。
- **本次的动态商品事实**：型号/参数/微信打印兼容方式/耗材/售后、报价/库存等；必须通过对应来源核查，不得由选择框架或大模型凭空推导。

## 2. 推荐的处理链

```text
用户说用途、预算、使用场景
  → 归纳确认的硬约束、偏好、未知与冲突（保留原话）
  → 识别品类，查本地可复用的知识/框架索引
  → 若缺关键品类认知，按需发现「技术路线/判断维度/关键例外」
  → 对候选框架逐项核查：来源、日期、市场、适用范围、独立性、反证、允许用途
  → 只追问会改变选择结果的缺口，不能让用户重复回答已给出的区间/约束
  → 用有资格的证据比较技术路线；证据不足时给具体缺口，而非空泛弃答
  → 如果任务确实要具体商品，再查在售型号与官方参数/独立实测
  → 准备购买时才查实时价格、库存与商家条款
  → 输出候选、淘汰理由、正反证据、剩余风险、时间戳与审计轨迹
  → 经复核的可复用认知进入知识索引；动态报价不当成长期知识
```

不提前为全世界品类制作完整知识库；遵守「只取足够做本次决策的最小证据集」。

## 3. 配置应描述什么，而不是什么

**概念性配置示意，字段名不是已定接口，也不表示以下专业结论已获证据批准：**

```yaml
category: printer
stage: route
decision_dimensions:
  - key: print_volume
    value_type: interval
    candidate_question: 每月大约打印多少页？
    why_it_matters: 影响成本和技术路线比较
  - key: home_color_required
    value_type: boolean
    candidate_question: 彩印是否必须在家完成？
  - key: idle_frequency
    value_type: duration
    candidate_question: 会连续闲置多久？
  - key: wechat_print
    value_type: compatibility
    verification: 型号级官方能力或可复现实测
candidate_routes:
  - monochrome_laser
  - inkjet
  - external_printing
evidence_to_find:
  - technical_principles
  - independent_comparisons
  - maintenance_and_consumables
unverified_claims: []
status: draft_unreviewed
```

空调可能需要房间面积、冷热场景、安装、能效和噪声；净水器可能需要原水条件、过滤路线、认证、换芯成本。**各品类可以有不同维度，底层的证据要求、约束检查和比较流程则应复用。**

配置至少要有：
- 维度名称、数据类型（布尔、区间、枚举、单位数值、文本等）、取值和未知语义；已确认/推测/待确认的来源。
- 为什么它可能改变选择、触发何种澄清、有哪些适用例外；不要把模型猜测标成专业结论。
- 候选路线与取舍主张；每条主张关联来源、反证、适用市场/型号/时间和复核状态。
- 配置版本、审批状态、失效/复核条件；无批准证据只能进入研究或暂缓路径。
- 对具体商品硬约束的核验状态（例如微信打印与一般 Wi-Fi 不等价），以及参数/报价快照的独立来源。

**禁止**把动态生成的配置变成可执行 Python/Java/脚本或让它绕过已冻结的校验规则；如将来需要空调负荷、总拥有成本等领域计算，优先引入单独评审、测试、版本化的受限计算插件，而不是按每次对话即时生成程序。

## 4. 与现有代码的关系（仅观察，不等于已实现）

- `shopping_decision/research_router.py`：已经能输出跨品类的待研究主题、可复用证据、应复核项目与动态核查计划；**尚未自动联网检索、核查真实性或给出跨品类推荐**。可作为未来流程入口。
- `docs/06_按需品类认知与跨品类复用.md`：已有 A 通用方法 / B 品类知识 / C 当前商品事实的三层分离。本备忘录是在 B 层增加「可审查的动态选择框架」，不另造一个全新知识体系。
- `shopping_decision/decision.py`：当前仍包含打印机条件分支；后续如验证成立，应该将公共的条件/证据/选项比较归入通用决策层，而非为每个新品类追加类似分支。
- `shopping_decision/contracts.py`：已有 `ProductCatalog` / `ProductSnapshot` 作为未来商品接入的契约轮廓，**并不代表具体商品目录与报价已接通**。
- Java Swing 和 Python 桥接：保持薄交互层；不在 Java 写第二套专业选购规则。若要动态展示维度，应先验证必要性与最小交互方案。

## 5. 建议的验证方式：先证伪/证实，再决定写什么

**当前不申请大规模重构。** 评估者可在现有 H08 真实打印机案例与一个差异较大的新品类（如空调/净水器）上做小样本设计：

| 验证问题 | 可观察的通过依据 | 常见失败方式 |
|---|---|---|
| 不同品类能否发现正确关键维度 | 独立专家/原始资料确认维度真正影响选择，并覆盖硬约束 | 模型编造指标，忽视安装/安全等关键条件 |
| 能否只补问必要问题 | 已给出的区间与约束不重复问；缺口与判断变化一一对应 | 通用问题清单反复追问 |
| 证据能否迁移/按需复用 | 资料按用途、日期、地域和产品范围筛选；保留反证 | 历史测试直接推出现售品牌排行 |
| 同一比较器能否处理不同路线 | 不为第二品类新增专用条件分支，仍能解释淘汰原因和条件 | 靠单一固定评分/品类硬编码得到答案 |
| 能否守住商品事实和授权边界 | 无官方型号核验则不承诺具体功能；无实时报价不报现价；不自动下单 | 把 Wi-Fi 当微信打印、把来源摘录当购买批准 |

可对比「现有固定品类逻辑」与「人工准备的受审品类配置 + 同一个通用比较流程」在相同需求/证据下的表现。先确认设计是否真的能少写品类代码、提升新类目适用性和解释质量，再决定是否自动生成配置、接在线检索或扩展界面。

无需为了试验先生产成百上千张知识卡，也不以弃答率低、自动测试全绿或模型自评作为专业正确性的唯一依据。记录证据获取成本、人工复核成本、约束漏失、误推风险以及配置重用情况。
