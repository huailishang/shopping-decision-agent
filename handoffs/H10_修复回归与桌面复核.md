## 唯一新增必修：P1，先waitFor再读完整输出，导致普通请求超时

位置：`desktop/ShoppingDecisionDesktop.java:96–98`。

当前顺序：创建子进程 → `waitFor(20秒)` → 再 `readAllBytes()`。子进程通过标准输出发送Base64编码的完整评审JSON。输出较长时，如果Java不持续消费管道，Python写入/结束阶段就可能等待管道被读取；Java却在等Python先结束。最终触发20秒超时并强杀本来能快速完成的后端。

这不是假设，也不是仅凭源码推测：

1. 实际Python桥接以 `subprocess.run(..., capture_output=True)` 持续收集相同正常输入，输出为 **5073字节**，其中 `report_json` 行 **4252字节**，可正常结束。
2. 独立Java进程探针调用同一个真实Python桥接，不启GUI、不给源卡增加批准；仿当前“先等待后读取”时 **3秒仍未退出**，可见已有5073字节待消费；对照改为读取线程先启动并持续消费，**本次约295毫秒退出**，读到相同5073字节。
3. 编译最新Swing源码并新开窗口，完整执行输入→补充→确认，**真实弹出20秒超时提示**；修改为缺彩色条件的较短响应，可进入结果页及评审预览。

不要把本次5073字节误当作跨平台固定的管道容量阈值。结论是当前I/O顺序依赖输出大小，现有正常数据已经触发；增加超时不能消除互等。

```java
import java.io.*;
import java.nio.charset.StandardCharsets;
import java.util.*;
import java.util.concurrent.*;
public class H10PipeProbe {
    static void probe(String python, boolean drain) throws Exception {
        var cmd = new ArrayList<>(List.of(python, "-m", "shopping_decision.desktop_bridge"));
        for (var s : new String[]{"printer test", "200", "", "", "false", "", "", "", ""})
            cmd.add(Base64.getEncoder().encodeToString(s.getBytes(StandardCharsets.UTF_8)));
        var p = new ProcessBuilder(cmd).redirectErrorStream(true).start();
        var reader = new Thread(() -> {
            try { p.getInputStream().readAllBytes(); } catch (IOException ignored) { }
        });
        if (drain) reader.start();
        boolean finished = p.waitFor(drain ? 10 : 3, TimeUnit.SECONDS);
        System.out.println("drain=" + drain + ", finished=" + finished);
        if (!finished) { p.destroyForcibly(); p.waitFor(2, TimeUnit.SECONDS); }
        if (drain) reader.join(2000); else p.getInputStream().close();
    }
    public static void main(String[] args) throws Exception {
        probe(args[0], false); probe(args[0], true);
    }
}
```
